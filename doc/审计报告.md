## 0. 总体评价（TL;DR）

这是一个**架构清晰、文档极其详尽、可测性意识强**的 Windows 桌面 C++ 项目。核心亮点：

- 分层依赖单向且可执行：`ui → core → services → native`，`Store` 通过 `IStoreStorage` 注入生产/单测，UI 与核心逻辑彻底解耦、可单测。
- 全量 RAII（`Com<T>` / `ClipbrdLock` / `GlobalMem` / `MenuGuard` / `ProcessHandle` / `ScopeExit`）；`AppContext::Shutdown` 有固定顺序的清理链。
- 单 UI 线程 + 分段异步（6 类定时器），无锁设计有清晰前提，文档 §9 明示"三窗口必须同线程"这一假设。
- 持久化三级降级（`ReplaceFileW → MoveFileEx → 删除后 move`）+ 损坏数据逐条跳过 + 64MB 上限保护 + 日志 1MB 尾部保留轮转。
- 文档一致性：`doc/DESIGN.md §0.1` 用 C1–C13 固化了 13 个文档矛盾取值、`§14` 有 T1–T6 决议、`§15` N1–N9 风险登记；`doc/PROJECT.md` 附录 A 给出逐 API 白名单与"禁止出现"清单。这是**契约级设计**，可复现性极强。

主要风险集中在**工程化与验收闭环**：MSVC 主构建缺一个链接库（`wtsapi32`）、若干用户决议（署名、图标）未落到代码/资源、发布打包脚本未落地、无 CI、无 CHANGELOG。逻辑层质量扎实，UI 层的实机验证仍有多处"未验证"。

**综合评级：良好（可交付前须先修 1 个 P0、3 个 P1；其余 P2 可并入下一步迭代）**。

## 2. 代码质量

### 2.1 亮点

- 全量 `W` 后缀 API；`UNICODE/_UNICODE`；`/utf-8`；`NOMINMAX`；命名规整（类型 `PascalCase`、成员尾下划线、常量 `kPascal`、文件与类同名）。
- 关键边界处理严谨：`TrimToLines` 二分上界 400 字且不切代理对、`Parse` 的"列号/行号不前移"、`JsonParse` 的 `\u` 代理对重组、`FromUtf8` 的坏字节替换 U+FFFD 不抛异常、`ParseIso` 兼容"无后缀/带毫秒/带 ±hh:mm"三种时间形态。
- 性能意识：搜索用预计算折叠键（`foldContent/foldLabel`），运行期纯 `std::find`；`LayoutCache` 按 `const ClipItem*` 缓存 DWrite 布局，宽度变化整体清空、条目消失逐条剔除；列表绘制做视口裁剪 + 遮挡跳帧。

### 2.2 质量缺陷（按严重级）

| # | 项 | 严重级 | 位置 | 说明 |
|---|---|---|---|---|
| Q1 | **MSVC 主构建缺链接 `wtsapi32`** | **P0** | `CMakeLists.txt:70-72`（`SuperClip` 目标）+ `MainWindow.cpp:5`（`#include <wtsapi32.h>`）+ `MainWindow.cpp` `WTSRegisterSessionNotification` | 主目标 `target_link_libraries` 只列了 `user32 kernel32 shell32 gdi32 advapi32 ole32 oleaut32 uuid bcrypt d2d1 dwrite`，**没有 `wtsapi32`**。`WTSRegisterSessionNotification` 由 `wtsapi32.dll` 导出，MSVC 下需要 `wtsapi32.lib` 才能解析。后果：`build.bat` 走 MSVC Release 会 **LNK2019 未解析外部符号**，主程序无法链接成功。交叉构建路径（`build-tests.sh`）显式加了 `-lwtsapi32` 所以能过——**这恰恰掩盖了 MSVC 主路径的断链**。这是"主发布路径不可编译"的硬伤，必须修 |

| Q3 | `PasteService::WriteClipboard` 重试间用 `Sleep` 阻塞 UI 线程 | P2 | `PasteService.cpp` | 写盘重试 `3×25ms` 用 `Sleep(kReadRetryMs)` 阻塞；与文档 §5.2"上限低于一帧两倍"自洽，但这是全程序唯一一处同步 `Sleep`。文档已声明可接受，但建议后续改为与读侧一致的 `SetTimer` 分段，消除 UI 线程微停顿 |
| Q4 | `Boundary()` 每次 O(n) 遍历 | P2 | `Store.cpp` | `std::count_if` 全表数收藏；`EnforceLimit/MoveToBack/ClearAll/Reset/AddFromClipboard` 都调用它，单次操作可达 O(n²)。n≤500 时实测无感，但收藏条数无上限（C12 副作用）时随时间劣化。可维护 `favoriteCount_` 增量计数 |

## 3. 安全性

### 3.1 亮点（本项目安全姿态较好）

- **零网络代码**（AC-8 红线）：无 `ws2_32/winhttp/wininet/urlmon`，附录 A.3 显式列"禁止出现"清单，且用 `dumpbin /dependents` 结案——安全面极小。
- **剪贴板数据本地化**：不上传、不留遥测；`error.log` 只写本地 `%AppData%`。
- **无管理员提权**：manifest `asInvoker`；`Local\` 会话级互斥体（T1）避免 `Global\` 需 `SeCreateGlobalPrivilege`。
- **原子写 + 64MB 读上限 + 日志 1MB 轮转**：防数据文件与日志被写坏/撑爆。
- **`UIPI` 边界**（N5）：不主动提权注入提权窗口，失败静默，符合最小权限。

### 3.2 需关注项

| # | 项 | 严重级 | 位置 | 说明 |
|---|---|---|---|---|
| S1 | **全局低层鼠标钩子 `WH_MOUSE_LL`** | P2 | `ProcessPicker.cpp` | 点选期间安装系统级低层钩子并**替换系统光标**（`SetSystemCursor`）。这是"点选绑定"的既定设计（T2），但低层钩子若卡死会被系统按 `LowLevelHooksTimeout` 摘除；代码已做"钩子内只做 `WindowFromPoint`+`PostMessage`，进程名解析留主线程"的优化。风险在于：**点选期间全局鼠标被本进程钩子接管**，若 `Cancel()` 链某条路径漏执行，理论上可影响系统鼠标。现有 6 条取消路径 + `EndPick` 幂等 + `SPI_SETCURSORS` 一键复位已较完备，建议补一条"钩子存活但主窗已销毁"的兜底 |
| S2 | **`SendInput` 模拟全局键盘输入** | P2 | `Keyboard.h` | 粘贴用 `SendInput` 发 Ctrl+V。这是剪贴板工具的固有能力，风险是若前台切换逻辑异常（N9 未定论项），按键可能落到**非预期窗口**。已有"三段夺前台 + 60ms 焦点等待 + 失败仍在当前前台"的降级，但 N9（个别第三方应用 2/9 未进入粘贴分支）是**未闭环**风险，建议步骤 12 前多目标多样本复测 |
| S3 | **粘贴会覆盖系统剪贴板** | P3 | `Clipboard.cpp` `WriteClipboardText` | `EmptyClipboard`+`SetClipboardData` 会替换用户当前剪贴板内容。这是 FR-11 的固有语义（"写剪贴板→Ctrl+V"），非缺陷，但应在帮助/文档中明确告知用户"使用 SuperClip 粘贴会覆盖你刚复制的内容"。当前帮助窗未提此副作用 |
| S4 | **`history.json` 明文存储剪贴板内容** | P3 | `StorageService.cpp` | 剪贴板可能含敏感信息（密码、token、个人数据），落盘为**明文 UTF-8** 在 `%AppData%`。这是 `.NET 版同目录同格式`的兼容性硬要求（§8.2），不能单方面加密（会破坏两版互通）。属**产品取舍**而非代码缺陷，但应写入"数据与隐私"说明，并评估是否提供"退出即清除明文"或"仅内存不落盘"选项 |
| S5 | **SHA-256 失败返回空串 → 去重键失效** | P3 | `Sha256.cpp` | `HexSha256Utf8` 任何 BCrypt 失败返回 `L""`；`Store` 用空 hash 项仍会入列。注释称"调用方据此拒绝入列（不做二次去重）"，但 `Store::AddFromClipboard` **实际没有检查空 hash 就入列**。即 BCrypt 异常时：去重失效 + 落盘 `Hash:""`。BCrypt 失败概率极低（系统组件），但"注释与行为不符"是隐患，建议二选一：真拒绝入列，或删掉那句注释 |
| S6 | **日志写失败/路径不可写无告警升级** | P3 | `Log.cpp` | `AppendUtf8` 失败直接 `return`（静默）。`%AppData%` 不可写时，`StorageService` 有"状态栏红字"（§8 降级表），但 `error.log` 本身不可写时无任何用户可见反馈。可接受，属极端场景 |

## 4. 依赖与许可证

### 4.1 结论：依赖面极小，全部系统自带或宽松许可

| 依赖 | 来源 | 许可证 | 评估 |
|---|---|---|---|
| Win32 / user32 / kernel32 / shell32 / gdi32 / ole32 / oleaut32 / advapi32 / uuid / wtsapi32 | 系统 | Windows 系统 API | 无第三方 |
| bcrypt（SHA-256） | 系统 | 系统 | 免第三方，符合 FR-02 |
| d2d1 / dwrite / dwmapi（动态加载） | 系统 | 系统 | UI 渲染 |
| C++ 标准库 + `/MT` 静态 CRT | MSVC | 商用许可 | 目标机免运行库（AC-7） |
| **RapidJSON**（设计方案 ADR 选定） | 第三方 MIT | MIT | **实际未使用**——见 D1 |

**关键点 D1（依赖声明与实现不符）**：`doc/DESIGN.md §1` 与 `doc/PROJECT.md §10` 都写"JSON 用 RapidJSON（header-only, MIT）"，但实际代码用的是 `src/core/Json.h/.cpp` 的**自研 300 行极简 JSON 解析器**（`Json.h` 注释明说"原 ADR 选 RapidJSON，但当前环境离线无法取包 → 内置 180 行实现"）。
- 这本身**不是缺陷**（自研 JSON 面更小、零依赖、读侧兼容 `\u` 转义），反而更符合"依赖从简"。
- 但**文档（设计方案 §1、§12、技术方案 §10.1）仍写着 RapidJSON**，与实际实现矛盾。这是"文档滞后"，应在下一轮同步时把 JSON 选型 ADR 改写为"自研极简解析器"，避免后来者误以为要引 RapidJSON。

### 4.2 许可证合规
- 全项目零第三方代码（RapidJSON/Catch2 均未实际引入），**许可证零风险**，可商用。
- `agent.md` 的"依赖从简、许可证可用"红线**达成**。
- 注意：`dwmapi` 在 CMake 注释里说"走 LoadLibrary，不入链"，但 `target_link_libraries` 实际**没有**列 `dwmapi`（`SystemInfo.cpp` 确实 `LoadLibraryW` 动态加载）——**此处文档与代码一致**，是正确做法。
